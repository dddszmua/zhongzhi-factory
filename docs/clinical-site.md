# 临床专站实现与接口约束

## 当前前端行为

- 公开算法目录、搜索、首页推荐、收藏、详情直达、MCP 目录和 MCP 详情统一使用 `isClinicalListed`。只有 `domain=health`、说明卡完整且 `reviewStatus=approved` 的服务可见。
- 旧服务没有 `ZZF_CLINICAL_V1:` 说明卡时默认不公开，需由项目团队归类和补录。私有「我的临床模型」列出待归类历史模型。
- 新提交的说明卡编码在 `source.companyIntroduce` 中，且 `reviewStatus` 固定为 `pending`。编辑展示信息后重新进入待审核。`source.msIntroduce` 保留摘要。
- 结构化二分类评估页在浏览器本地读取 CSV，检查患者是否跨集合、结局标签和概率范围；计算测试集/外部集的敏感度、特异度、阳性预测值、AUROC、AUPRC、Brier 分数和校准分组。可选 `baseline_score`、`group`。

## 上线前必须由复用后端实现

当前项目只有前端。前端筛选无法阻止调用旧平台 API，也不能构成真实上架审核。后端需要为临床站点增加独立的目录接口和站点上下文，并在服务端完成以下检查：

1. 读接口：列表、搜索、智能搜索、详情、收藏、MCP 目录均只返回已批准的临床服务；私有作者列表可返回本人待审核/待归类项。直接访问服务 ID 也必须检查。
2. 写接口：作者只能提交 `pending`，不能修改 `reviewStatus` 为 `approved`；具备审核权限的角色记录审核人、时间、理由和说明卡版本。修改名称、用途、输入输出、模型文件或证据后撤销原批准。
3. 临床元数据建议迁移到独立表或 JSON 字段，包含适用人群、排除条件、字段与单位、缺失处理、输出、预测时域、阈值、数据来源、样本量、验证设计与结果、版本、团队、参考文献和限制。当前编码在 `companyIntroduce` 只是兼容旧服务结构。
4. MCP 工具在运行时校验参数类型、单位、范围、缺失值与适用人群，并在响应中附上模型版本、结果含义、适用范围与提示；模型文件、预处理代码和字段规范应固定同一版本。协议连通测试不能替代临床验证。
5. 真实患者数据的上传、存储和调用应走项目授权路径。当前评估页只在本地处理文件，不能替代院内数据治理与正式研究流程。

## 评估 CSV 格式

```csv
patient_id,outcome,score,set,group,baseline_score
P001,1,0.82,test,adult,0.62
P002,0,0.18,test,adult,0.25
```

`set` 可为 `train`、`test`、`external`。`group` 和 `baseline_score` 可省略。上传前需将患者 ID 去标识化，并确保 `score` 来自锁定版本模型对验证集的真实预测。当前评估页不计算置信区间、决策曲线，也不自动核查原始特征的医学单位和时间泄漏；这些项目仍需在正式研究中完成。
